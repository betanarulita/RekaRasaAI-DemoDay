# Content Planner UX audit

Mode: AFTER. This report records current findings; no application code or configuration was changed.

## Findings

### 1. LOW — Brief submission requires fixed output choices

**Rule:** R-05 / Craftsmanship C-3 — page structure should follow the user's actual task.

The new brief form requires one or two checkboxes before it can submit. `newPage()` in `static/app.js` renders only TikTok and marketplace choices, and its submit handler rejects an empty selection. The `/api/plan` handler in `app.py` repeats that requirement and tells Planner to return exactly the selected formats. A brief alone therefore cannot reach Planner.

### 2. LOW — Planner proposals cannot represent the requested range of deliverables

**Rule:** R-05 / Craftsmanship C-3 — the plan structure should serve the content request.

`PLAN_SCHEMA` in `app.py` accepts at most two tasks. The `/api/plan` and `/api/confirm-plan` handlers whitelist TikTok and marketplace formats (plus a legacy social-video alias). `renderPlanReview()` in `static/app.js` offers only the same two formats, limits additions to two tasks, and derives platform from the selected format. The schema has no short output rationale field. Poster, static ad, product hero image, storyboard/visual work, campaign bundles, and custom formats cannot be proposed faithfully.

### 3. LOW — Writer instructions are specialized only for TikTok and marketplace

**Rule:** R-05 / Craftsmanship C-3 — task structure should reflect the selected deliverable.

The initial Writer prompt in `app.py` gives explicit structure only for TikTok scripts and marketplace descriptions. New formats would pass through without format-specific guidance, even if Planner and task validation were expanded. Writer and Reviewer can otherwise receive task title, format, platform, angle, and goal, so this likely needs a targeted prompt extension rather than a workflow rewrite.

### 4. LOW — Failed Planner calls leave a saved brief without a plan

**Rule:** R-26 / Craftsmanship C-2 — the form action should complete cleanly and give a consistent retry path.

`/api/plan` commits the conversation, user message, and brief before calling the model. If inference fails, no plan or task is created, but the saved conversation/brief remains. A retry without the existing conversation ID can leave duplicate history entries. There is no partial task creation, but the failed request is not transactionally clean.

## Audit notes

- Existing edit/confirm flow retains title, format, angle, and goal editing. Confirmation writes task rows and `plan.confirmed` audit events; task approval and remediation logic are separate from format selection.
- Migration 002 adds task title/platform/angle/goal columns with defaults and preserves existing rows. Existing TikTok and marketplace task formats remain readable. No database migration is indicated for making output preferences optional.
- Current tests exercise the two-output TikTok + marketplace workflow and a schema-valid Groq response. They do not cover a brief without formats, a poster request, a custom preference, an output rationale, or no-invented-facts behavior for these new planning cases.
- `python -m unittest -q test_app` ran 30 tests: 28 passed and 2 failed. Both failures are image tests that assume OpenAI is selected; the local `.env` selects a different configured image provider. The tests need provider isolation. `.env` was left untouched.
- Image text overlay/editor is not implemented. The workbench can generate and save a raster visual, but has no separate headline/body/CTA overlay fields or compositing step. Do not rely on SD 1.5 for accurate rendered copy.
- UI behavior was inspected in code; no browser click-through was performed during this audit.

## Suggested implementation order

1. Make `formats` optional in the request; persist an empty preference list and ask Planner to infer one or more deliverables from the brief and project sources.
2. Add a concise `selection_reason` to each Planner task, extend the local schema and provider prompt, and validate task count/fields without forcing equality to requested preferences. Preserve the current format whitelist only where needed for legacy, or extend it with a safe non-empty custom format and explicit platform handling.
3. Update the proposal editor to render Planner formats dynamically, keep preference controls optional, and let users edit title, format, angle, and goal as today. Preserve the existing confirmation API's protection against empty titles/angles/goals.
4. Extend Writer prompt guidance only for the new output classes needed by the demo; keep source and approval rules intact.
5. Add fake Planner/Writer tests for no preference, poster preference, TikTok + marketplace preference, missing facts, model failure before task creation, old task reads, and existing approval/revision behavior. Isolate image provider settings in the existing tests first.
6. Treat text-on-image overlay as a separate small feature: keep generated imagery text-free and compose headline/body/CTA with a basic editor only after a rendering approach and preview flow are selected.
